LLM Tool Calling Lab: What the First Release Changed

A local chatbot can fit useful ML models and still give an unreliable answer. My first release makes that gap visible and sets the next engineering priorities.

First-pass finding

Added planning instructions did not improve grounded completion in the frozen synthetic campaign: 31/48 structured conversations passed versus 33/48 generic conversations.

The question I wanted to answer

I want a conversational ML tool that lets a developer inspect the analysis behind an answer: which method ran, which data it used, and what its output can support. LLM Tool Calling Lab is my first local reference implementation of that idea.

The first published version is v0.1.0, an experimental release. It turns numerical questions into bounded tool calls, records the results, and lets a follow-up use that evidence. I also tested whether explicit planning instructions improved the conversation. They did not improve the measured completion rate in this first pass.

What I built

The app runs a local Qwen3 model through Ollama, with a Streamlit chat interface and eight scikit-learn methods. It supports numerical prediction, binary classification, unusual-row ranking, and exploratory grouping. Each family has two eligible methods. Supervised and clustering outputs cover validation rows; anomalies can score a separate fresh batch.

I kept fitting logic outside model-generated text. No generated code executes. The same budget covers the initial question and follow-up: two fits, eight tool calls, six LLM responses, one repair, 4,096 generated tokens and 180 seconds of system work. A failure consumes its allowance instead of disappearing behind unlimited retries.

A run in the local app

For the screenshots, I used the included synthetic regression example on the running local server. This is an illustrative run after release, not another held-out benchmark case.

The first answer fitted Random Forest: validation mean absolute error was 0.7686 versus 3.0326 for the training-median baseline. Lower MAE is better on these validation rows. The evidence panel reads the saved values directly. The answer still described the difference as significant without a significance test, and said no further action was needed. I would keep the measurement and reject those stronger conclusions.

I then asked for the other eligible method. Ridge returned validation MAE 0.1420 on the same partition, and the follow-up preferred its lower validation error over Random Forest's 0.7686. The scrolled view shows both recorded results. The episode used two fits, three tool calls and five model responses, with no repair. This demonstrates a consequential comparison on one synthetic example; the automatic 'no further action' statement still does not establish readiness for real data.

How to read this demo

Recorded metrics and the assistant's interpretation have separate checks. Unsupported significance language or an incomplete comparison is a limitation of the displayed answer, even when the model fit succeeds. This run is excluded from every campaign count.

What the frozen comparison found

The campaign compared generic tool calling with the same LLM given an explicit planning workflow. Both conditions shared the backend, tools, data access and budgets. Fixed methods supplied separate model-quality references; they were not conversational competitors.

All 168 required records are complete: 16 development conversations, 96 supported held-out conversations, 24 separate challenge conversations, and 32 deterministic references. Grounded completion requires structural validity and every applicable qualitative check across both delivered turns. A later correction does not erase an earlier unsupported claim.

Only 5/24 anomaly conversations passed every check. Invalid answers and evidence citations dominated the structural failures; other episodes fitted another method but missed the requested comparison. The challenge suite exposed unsupported forecast proposals and data-limit handling. Clustering reached the synthetic model-quality ceiling, so those fixtures offer little evidence about harder grouping problems.

Scope of the finding

Qualitative scores are unblinded AI assessments by implementation agents. There was no independent human review or user study. These small synthetic results support no significance, general superiority, production-reliability or reduced-expertise claim.

What worked—and what I would keep

The reusable part is the boundary between conversation and execution. A common specialist interface made methods replaceable; the executor made their evidence inspectable. The released Windows installation passed 102 automated checks, and two artifact audits covered all 168 records without findings in their checked invariants. Those audits did not independently recompute every model metric.

The extension tutorial actually replaced Ridge with ElasticNet and fitted both configurations. A fresh installed-wheel conversation also compared Random Forest with ElasticNet. That proves a working replacement path. It does not prove that the explanation became reliable: the tutorial's first answer still used unsupported significance language.

The first campaign also failed before chatbot inference because of a relative-path runner defect. I preserved it separately. The replacement corrected the harness path, used fresh seeded data, and kept chat/model behavior unchanged. The two campaigns are not pooled.

The direction after this release

My decision is to keep the validated executor, shared limits, replaceable specialists and recorded artifacts. I will not describe the planning prompt as a demonstrated improvement. The generic condition remains the simpler comparison point for the next evaluation.

  1. Make anomaly answers usable

    First proposed slice: return valid cited selections in both turns and preserve the selected artifact when comparing methods. Keep invalid episodes in the score.

  2. Handle unsupported requests earlier

    Check task eligibility before proposing a fit. Explain invalid data and a useful next step instead of stopping at a tool error.

  3. Check the explanation and next action

    Treat unsupported significance language, omitted limits and actions that contradict a causal refusal as failures, even when the numbers are correct.

  4. Strengthen the next evaluation

    Use fresh, more varied held-out cases and independent blinded review. A claim about reducing users' expertise needs a separate human study.

These are proposed changes, not fixes shipped in v0.1.0. I will keep one bounded change active and evaluate a new version against simpler alternatives. The first release is useful because it gives me an inspectable starting point and specific failures to address. It also gives another developer enough source and evidence to question my choices.

Try it and inspect the evidence

Local inference used no paid API calls, but hardware and electricity costs were not measured.
